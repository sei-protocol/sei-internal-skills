# Reliability & resilience

Checklist for code and design that has to stay up while things around it fail. Our-own-words rules that point at the open canon — cite the authority in findings (see `sources.md`); never reproduce source text.

Sections: `## checklist` · `## severity model`. Anchors: Google SRE, Amazon Builder's Library, Fowler/Azure patterns, Principles of Chaos, 12-Factor.

## checklist

| id | principle | rule | cue | authority |
|----|-----------|------|-----|-----------|
| REL1 | Timeout every remote call | Every call that leaves the process gets an explicit deadline — including connect, TLS handshake, and read, not just the request body. A call with no timeout is a thread/goroutine you may never get back. | A client built with default (often infinite) timeouts; a `Dial` with no connect deadline. | Amazon Builder's Library: Timeouts/Retries |
| REL2 | Propagate deadlines | Carry the caller's deadline down the chain so the whole tree cancels together; derive child deadlines from the budget left, don't re-set fresh ones. A sub-call must never outlive the request that spawned it. | `context.Background()` started mid-request; a downstream call with a fixed timeout regardless of remaining budget. | Google SRE: Cascading Failures |
| REL3 | Bounded retries | Cap attempts; never retry forever. Retry only transient errors on operations safe to repeat. Retries multiply load exactly when the dependency can least take it. | `for { … }` retry with no ceiling; retrying a 4xx/validation error or a non-idempotent write. | Amazon Builder's Library: Timeouts/Retries |
| REL4 | Backoff with jitter | Space retries with exponential backoff plus randomized jitter so independent clients don't resynchronize into a thundering herd after an outage. | `sleep(1s)` between retries; `base * 2^n` with no random component. | Amazon Builder's Library: Backoff and Jitter |
| REL5 | Retry budget | Bound aggregate retries as a fraction of live traffic (a token/budget model), not just per-call — a per-request cap still lets a fleet-wide failure triple total load. | Per-call cap but no global limit on retry volume; retries scaling 1:1 with error rate. | Google SRE: Cascading Failures |
| REL6 | Retry at one layer | Pick a single layer to own retries; layers below pass failures straight up. Stacked retries compound multiplicatively (3 layers × 3 tries = 27). | Client, service, and gateway each retrying the same logical call. | Google SRE: Cascading Failures |
| REL7 | Idempotency keys | Make retried writes safe via a client-supplied idempotency key the server dedupes on, so a retry after an ambiguous timeout doesn't double-apply. | A POST/charge/enqueue with no dedupe key; "retry on timeout" on a non-idempotent mutation. | Amazon Builder's Library: Idempotency |
| REL8 | Shed load fast | Under overload, reject excess quickly and cheaply rather than queueing it — fast rejection frees capacity for what you can still serve. Slow failure is worse than fast failure. | No admission control; the server accepts everything and degrades for all instead of serving some well. | Google SRE: Handling Overload |
| REL9 | Bound every queue | Every queue, buffer, and worker pool has a hard ceiling; reject or shed when full. An unbounded queue turns a load spike into OOM and ever-growing latency. | A channel/queue with no capacity limit; a buffer that grows until OOM. | Google SRE: Handling Overload |
| REL10 | LIFO + prioritize under overload | When shedding, drop oldest/lowest-value first — serve newest (LIFO), since old queued requests have often already timed out client-side; prioritize by request criticality. | FIFO draining stale requests nobody awaits; all traffic equal-priority during a brownout. | Google SRE: Handling Overload |
| REL11 | Circuit breaker | Wrap a flaky dependency in a breaker that trips open after sustained failure, fails fast while open, and probes half-open before closing. Stops a dead dependency consuming all your threads. | Every call hammering a dependency that's been timing out for minutes; no fast-fail state. | Fowler: CircuitBreaker |
| REL12 | Bulkhead isolation | Partition resources (connection/thread pools, queues) per dependency or tenant so one saturated path can't starve the others. | A single shared pool for all downstreams; one slow dependency exhausting threads healthy ones need. | Azure: Bulkhead pattern |
| REL13 | Degrade deliberately | Design and exercise the reduced-function mode (serve stale, drop optional features, partial results). Planned, tested degradation beats cascading failure. | No defined "minimum viable response"; an all-or-nothing path that takes everything down when one piece fails. | Google SRE: Cascading Failures |
| REL14 | Beware the untested fallback | A fallback that only runs during incidents is your most dangerous code — cold, unexercised, failing exactly when invoked. Exercise fallbacks routinely or assume they're broken. | A `catch`/recovery branch with no test and no traffic until an outage triggers it. | Amazon Builder's Library: Avoiding Fallback |
| REL15 | Cache is not free capacity | Treat a cache as an optimization, not a load-bearing dependency: size the system to survive a cold/empty cache, or a flush/restart instantly overloads the backing store. | Origin DB provisioned only for cache-miss traffic; no plan for flush, eviction storm, or cold start. | Google SRE: Cascading Failures |
| REL16 | Liveness vs readiness | Keep the probes distinct: liveness = "should I be restarted?", readiness = "should I get traffic now?". Conflating them kills healthy-but-warming instances or keeps sick ones in rotation. | One `/health` wired to both probes; readiness OK before dependencies/caches are ready. | 12-Factor; Google SRE |
| REL17 | Graceful shutdown & drain | On termination signal: stop accepting new work, finish/hand off in-flight, then exit within the grace period. Hard exit drops in-flight requests and corrupts at-least-once handoffs. | No SIGTERM handler; immediate exit on shutdown; readiness still green while draining. | 12-Factor: Disposability |
| REL18 | Limit blast radius | Partition into cells/shards and roll out progressively (canary → stages) so a bad deploy or poison input damages a fraction, not the whole. Blast radius is a design choice. | A single global deploy to 100% at once; one shared instance for all tenants with no isolation boundary. | Principles of Chaos; Google SRE: Canarying |
| REL19 | Verify resilience with chaos | Treat resilience claims as hypotheses to test under realistic injected faults — an untested failure mode is an unknown one. *(Advisory / cut-first — un-defer once the timeout/retry/breaker floor is in place and staging fidelity supports safe experiments.)* | Resilience asserted in design docs but never exercised; "we think it fails over" with no game-day evidence. | Principles of Chaos |

## severity model

- **correctness/safety** — REL1 (no timeout = leaked resource/hang), REL2 (un-propagated deadline outlives its request), REL7 (non-idempotent retry double-applies), REL9 (unbounded queue → OOM). Bugs, not preferences; lead with them.
- **consequence-under-load** — REL3–REL6 (retry amplification), REL8, REL10 (overload behavior), REL11–REL12 (dependency-failure containment), REL15 (cache-as-capacity collapse), REL16–REL17 (probe/drain mishandling that drops traffic), REL18 (blast radius). Correct in steady state, dangerous under stress.
- **advisory** — REL13–REL14 (degradation discipline), REL19 (chaos verification). Raise them; don't gate on them.
