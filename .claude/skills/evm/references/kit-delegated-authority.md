# Delegated authority (on-chain) kit

## 1. What this concern is

On-chain **delegated authority** is granting a **scoped, revocable, time-bounded capability** that a *contract* enforces — the cross-org access-gating / agent-authority pattern: an **ERC-7710/7715 caveat-based delegation** redeemed on an **ERC-4337 session key**. The generic habit this corrects is building a **bespoke permission server** — which makes the operator the trusted party. That is correct *intra-org* (the org is its own trusted operator) but **wrong across an org boundary**, where mutually-distrusting parties have no operator either side trusts; the authority must live somewhere neither party runs (a chain). The decision rule is the **W3 test**: put authority on-chain **only when a contract must atomically react to it** (gate access, release a bond, advance a proposal). W1-alone (no-trusted-operator existence/ordering) earns only **"anchored"** — an off-chain EIP-712-signed log + one Merkle root per epoch — *not* on-chain-native. The 7710/7715 RPC surface is **Draft and recently renamed** — depend on the caveat *model*, build behind an adapter, never hard-wire the RPC name. *Cited (design):* omni `01-research/R11-cross-org-delegated-authority.md`, `03-architecture/onchain-auth-integration.md` (the W1/W2/W3 boundary); `sources.md` §erc7710, §erc7715.

## 2. The pattern (how to do it)

**At a glance:** a three-layer stack — an **ERC-4337 session key** (account) requests a permission via **ERC-7715** and redeems an **ERC-7710** caveat-enforced delegation through a Delegation Manager — issued by an **m-of-n grantor** and **self-deployed on Sei via CREATE2**. **Maturity gates every choice below:** the 4337 session-key layer + the caveat-enforcer *model* are architecture-stable; the 7710/7715 RPC surface is **Draft/pre-1.0 with a recently-renamed API — depend on the model, build behind an adapter, never hard-wire the RPC name** (full tiers at the end of §2).

- **The W1/W2/W3 boundary (earn the chain).** On-chain-native **iff W3** (a contract acts on the record). Everything else defaults off-chain-signed (EIP-712) + a per-epoch Merkle anchor. Keep the on-chain core minimal; push fine semantics to the enforced off-chain edge. *Cited:* `sources.md` §sei (omni `onchain-auth-integration.md` boundary table — 3 of 11 functions are on-chain-native: access-gating, bonding, registry).
- **The three-layer stack:**
  - **Account — ERC-4337 session key** (a validator module on a smart account, or an **EIP-7702**-upgraded EOA). Time-boxed by `validateUserOp`'s packed `validationData` (`validAfter`/`validUntil`; `validUntil == 0` = no expiry) — **note the low-20-bytes `authorizer` field (`0` = success, `1` = failure) shares that packed word, so a mis-packed return value can silently disable the time bounds.** EntryPoint **v0.6 / v0.7 / v0.8** (v0.8 current: native EIP-7702 support + EIP-712 UserOp hashing). EIP-7702 is **Final** (shipped in Pectra, 2025-05). Live on Sei via **Pimlico** — **chainId 1329 (mainnet)** confirmed; **1328 (testnet)** verify-before-use; ~400 ms finality is favorable for interactive grant approval. *Cited:* `sources.md` §erc4337, §eip7702.
  - **Permission request — ERC-7715.** The delegate requests a scoped, time-bounded permission as a **caveat set**. **RPC name (Draft, recently renamed — read this):** the canonical spec (post-2026-01-16) is **`wallet_requestExecutionPermissions`** (+ `wallet_revokeExecutionPermission`, `wallet_getGrantedExecutionPermissions`); **MetaMask's shipping implementation still exposes the legacy `wallet_grantPermissions`**. There is **no** `wallet_revokePermissions`. Pin to the wallet you target and re-verify at build time. *Cited:* `sources.md` §erc7715.
  - **Delegation + redemption — ERC-7710.** The grantor signs an **EIP-712 delegation**; the delegate redeems via the **Delegation Manager** — `redeemDelegations(bytes[] permissionContexts, bytes32[] modes, bytes[] executionCallDatas)` (**plural, batch**) — which validates **every caveat enforcer** before executing. Reference impl: MetaMask **Smart Accounts Kit** (formerly "Delegation Toolkit"); the on-chain contracts are in **`MetaMask/delegation-framework`**. Audited by Consensys Diligence (**Aug 2024** core; **Apr 2025** for `MultiTokenPeriodEnforcer`). **Pre-1.0**; CREATE2-self-deployable (`SimpleFactory`). *Cited:* `sources.md` §erc7710.
- **Caveat enforcers = the scoping vocabulary** (confirmed in `delegation-framework/src/enforcers/`, ~40 total): `AllowedTargetsEnforcer`, `AllowedMethodsEnforcer`, `AllowedCalldataEnforcer`, `TimestampEnforcer`, `LimitedCallsEnforcer`, `NonceEnforcer`, `ValueLteEnforcer`, `ERC20PeriodTransferEnforcer`. Composable. For pinning the scope bytes exactly, prefer **`ExactCalldataEnforcer`** / `ExactCalldataBatchEnforcer` (byte-exact match) over `AllowedCalldataEnforcer` (which constrains only a sub-range, so it can leave the rest of the calldata open) — the byte-exact form is the hardening default against the over-broad-caveat failure (§3).
- **The capability-grant pattern (the key move).** A resource *read* is not a native EVM action, so make the on-chain artifact a **capability grant**: a delegation whose **target** is your access-gate contract and whose **calldata** encodes the scope; an off-chain **policy-enforcement-point (PEP)** verifies the delegation on-chain and resolves the coarse on-chain scope → fine resource access (the chain can't see the resource). **On-chain = the authority root; off-chain = fine enforcement.** Map the enforcers to scopes: `AllowedTargets`→resource/namespace, `AllowedMethods`→op-class (read/derive/subscribe), `AllowedCalldata`→the dimensional slice, `Timestamp`→window, `LimitedCalls`→budget, `Nonce`→revocation. A custom scope-enforcer (decode + validate the declared scope shape) is the natural hardening so the PEP isn't the sole interpreter.
- **Revocation — three mechanisms, three latencies.** (1) **`NonceEnforcer` bump** — authoritative, instant at finality (~400 ms on Sei); kills the whole delegation. (2) **Session-key `validUntil` / `TimestampEnforcer`** — automatic backstop, bounds worst-case exposure. (3) **PEP refusal** — **subscribe to delegation-state, don't poll**; serve cross-org from a neutral or grantor-run node, never the consumer's.
- **EIP-712 approval + the verifier chain.** A human approval is an **artifact-bound EIP-712 struct** (e.g. `ArtifactApproval{artifactHash, version, action, approver, nonce, deadline}`) — **NOT SIWE** (SIWE authenticates a session; it does not approve an artifact). Verify signatures with the universal chain: **ERC-6492** (counterfactual/undeployed smart account) → **ERC-1271** (`isValidSignature` → magic `0x1626ba7e`, deployed smart account/multisig) → `ecrecover` (EOA). Harden multi-account replay with **ERC-7739** (nested-712 binds the account address). Clear-sign the grant with **ERC-7730** so m-of-n signers see scope + window human-readably. **Two distinct signature checks — don't conflate them:** the **Delegation Manager** verifies the *delegation* signature against **its own EIP-712 domain** (`SetDomain` — name/version/chainId/contractAddress; it runs the ERC-1271 check when the grantor is an m-of-n Safe); your **gate** verifies an *artifact-approval* signature. The EIP-712 domain **MUST bind `chainId` + `verifyingContract` here** (the EIP keyword is SHOULD; this kit treats it as **required** for replay scoping across `pacific-1`/`atlantic-2` — §4 Dimension 1 checks it). *Cited:* `sources.md` §eip712, §verifier-chain.
- **Governing the grant authority (the crown jewel).** The grantor should be an **m-of-n smart account** (Safe — CREATE2-self-deployable via `safe-singleton-factory`) + a **timelock** on privileged writes (Zodiac **Delay** modifier). The **registry** that maps namespace → authorized-signer is the highest-leverage attack surface — harden it (§3, §5). *Cited:* `sources.md` §safe-zodiac; omni `R9`/`D-016`.
- **Off-chain attestation default.** Provenance/approval attestations default to **off-chain EIP-712-signed** + a per-epoch Merkle anchor — this is EAS's own recommended path (EAS off-chain attestations are `signTypedData`; on-chain UID timestamping is the anchor). EAS is not native on Sei; off-chain-signed sidesteps self-deploy. *Cited:* `sources.md` §eas.
- **Sei deployment reality.** ERC-4337 is live (Pimlico, EntryPoint v0.6/0.7/0.8) — **chainId 1329 (mainnet)** confirmed, **1328 (testnet)** verify-before-use. **Self-deploy** the Delegation Manager + enforcers + Safe via **CREATE2** (not Sei-native). **Anchor-don't-stream:** SSTORE is governance-mutable and high (~72k mainnet) → prefer off-chain signed delegations + an on-chain nonce/anchor over storing every grant. **Shard the nonce space per namespace/delegator** — a single hot nonce/registry slot serializes under parallel-execution (OCC) contention. **Dual-address association:** a freshly-derived agent `0x` address may need an association step before cross-VM visibility (fold into provisioning). **EntryPoint addresses on chainId 1328 are verify-before-use** — not published here; confirm the live deployment before wiring. *Cited:* profile §2, §5, §9, §10.

**Maturity tiers (design accordingly):** *architecture-stable* — ERC-4337 session keys on Sei + the caveat-enforcer *model*; *depend on the pattern, not the API* — ERC-7710/7715 + the toolkit (Draft, pre-1.0, renamed RPC → adapter + self-deploy + version-pin); *track, don't build on* — **ERC-8004** (agent **identity/discovery/reputation only**, Draft — does NOT grant authority; keep authz in the 7710/7715/4337/7702 stack).

## 3. Anti-patterns / failure modes

- **Bespoke cross-org permission server.** Cue: an org-run ACL/RBAC service as the *cross-org* authority. Rewrite: on-chain 7710/7715 delegation; the server is a PEP that reads authority from chain (no operator is trusted across the boundary). *(Intra-org bespoke permissions are fine — the org is the trusted operator.)*
- **Hard-wiring the 7715 RPC name.** Cue: a literal `wallet_grantPermissions` / a guessed `wallet_revokePermissions`. Rewrite: an adapter over the RPC; the spec name is `wallet_requestExecutionPermissions` / `wallet_revokeExecutionPermission`, implementations lag — pin + re-verify.
- **Over-broad caveats.** Cue: a wildcard namespace root, no calldata dim-filter, no `LimitedCalls` budget. Rewrite: narrowest-scope (mandatory dim-filter — prefer **`ExactCalldataEnforcer`** for byte-exact pinning — + call cap + a scope-enforcer that **rejects wildcard roots**); the PEP **fails closed** on any scope it can't tightly resolve.
- **Treating redelegation as a "disable" caveat.** Cue: a grant that assumes a stock no-redelegate caveat exists. Reality: onward delegation is controlled by the **`Delegation.authority` field** (a root delegation's `authority` is `ROOT_AUTHORITY`; a sub-delegation's is the parent delegation's hash, and the Manager validates the whole chain in `redeemDelegations`) — **there is no stock max-depth caveat**. Rewrite: to forbid onward delegation, issue the grant only to a delegate that cannot re-sign (a constrained session key), or write a depth/leaf enforcer yourself.
- **Unbounded redeem-path gas (un-redeemable grant / DoS).** `redeemDelegations` loops over **every caveat enforcer (each an external `CALL`) and the whole delegation chain** before executing. A long caveat array or a deep chain makes redemption expensive — and on Sei, where gas is governance-mutable, a grant cheap to redeem at authoring time can become **uneconomic (effectively unrevocable-by-use)** later. Cue: an unbounded caveat array / no chain-depth bound. Rewrite: bound caveat-count + delegation-chain depth at authoring; treat a grant whose redemption gas exceeds a runtime-estimated ceiling as un-redeemable. `kit-evm-parity-gas`.
- **Streaming per-grant state on-chain.** Cue: an SSTORE per grant/revocation. Rewrite: off-chain signed delegation + on-chain nonce/anchor (anchor-don't-stream; SSTORE governance-mutable/high on Sei).
- **Single shared nonce / registry slot.** Cue: one global Delegation Manager nonce or registry slot written on every grant. Rewrite: shard per namespace/delegator (OCC serializes hot state — `kit-evm-parity-gas`).
- **Polling for revocation.** Cue: a PEP polling delegation-state on an interval. Rewrite: subscribe to the on-chain nonce-bump event; keep a short `validUntil` backstop.
- **Consumer-operated PEP for the grantor's namespace.** Cue: the consumer org runs the node serving the grantor's data. Rewrite: a neutral or grantor-run node; transparency-log every served read (fine enforcement is off-chain, so this is detection, not prevention).
- **SIWE-as-approval.** Cue: a SIWE login treated as artifact sign-off. Rewrite: artifact-bound EIP-712 approval — SIWE authenticates a session, it does not approve an artifact.
- **Blind-signing the grant.** Cue: m-of-n signers approve an opaque delegation. Rewrite: ERC-7730 clear-signing so signers see scope + window; keep the grantor m-of-n so one compromised signer ≠ a grant.
- **Decentralization-theater registry.** Cue: a "neutral" m-of-n that is really one team; a discretionary "Org X gets namespace Y" minter; no timelock; mutable forever. Rewrite: **no named winners** (an abstract open rule), m-of-n + **approve-slow / revoke-fast** timelocks, reference-value transparency, and **ossification — remove the lever, don't just distribute it**.
- **Assuming Safe/EAS are native on Sei.** Cue: code assuming a hosted Safe/EAS deployment. Rewrite: self-deploy via CREATE2; default attestations to off-chain-signed + anchor.

## 4. Review cues

- **Dimension 2 (access-control & privilege):** delegation scoped narrowest (target+method+calldata+time+limit), byte-exact where possible; no wildcard root; **onward redelegation forbidden by construction** (issued to a non-re-delegating delegate, or a depth/leaf enforcer — no stock disable caveat exists); the grantor is m-of-n + timelocked; the namespace→signer registry has no discretionary minter (no named winners). *Basis:* `sources.md` §erc7710; omni R9/R11/D-016.
- **Dimension 1 (security & exploitability):** EIP-712 domain binds `chainId` + `verifyingContract`; ERC-7739 multi-account replay hardening; `NonceEnforcer` revocation present + tested; verifier chain 6492→1271(`0x1626ba7e`)→`ecrecover`; **no SIWE-as-approval**; the registry / Delegation-Manager hardened as the crown jewel (m-of-n + timelock + irreversible + transparent). *Basis:* `sources.md` §eip712, §verifier-chain; omni threat model.
- **Dimension 3 (upgrade & storage-layout safety):** Delegation Manager + enforcers + Safe self-deployed via CREATE2 and **version-pinned behind an adapter** (Draft RPC churn); the gate's calldata grammar + the EIP-712 delegation typehash/domain (incl. the Manager's `SetDomain`) are one-way doors. *Basis:* §5; omni D-018/D-020.
- **Dimension 4 (external-call & value handling):** anchor-don't-stream (off-chain signed delegation + on-chain nonce); nonce sharded per namespace/delegator (OCC); the redeem path validates every caveat *before* executing; **caveat-count + delegation-chain depth bounded at authoring** so redemption gas stays within a runtime-estimated ceiling (Sei gas is governance-mutable). *Basis:* profile §2, §10.
- **Dimension 6 (testing & verification adequacy):** fork-test against Sei (4337 via Pimlico, chainId 1329/1328 — verify EntryPoint addresses first); test all three revocation paths + revocation latency; test that over-broad / wildcard scopes are rejected and the PEP fails closed. *Basis:* `sources.md` §foundry.

## 5. One-way doors in this concern

- **The registry / governance configuration** (the m-of-n set, timelock windows, the namespace→signer bindings) — the crown jewel; a compromise mints valid-looking authority for *anything*. Human approval + irreversibility discipline (ossify the root); never a quiet edit.
- **The access-gate contract's calldata grammar + the EIP-712 delegation typehash/domain** — a published interface delegations are signed against; changing it invalidates every outstanding grant. Flag.
- **The Delegation Manager's own EIP-712 domain** (`SetDomain` — name/version/chainId/contractAddress) — delegations are signed against it; redeploying the Manager or changing its domain invalidates every outstanding grant (a fourth domain-coupled door alongside the gate typehash). Flag.
- **A namespace→signer binding** (who may grant for a namespace) — a trust anchor, one-to-one and hard to walk back.
- **Self-deployed contract addresses** (Delegation Manager, gate, Safe) via CREATE2 — consumers and outstanding delegations depend on them; a redeploy breaks them.

**Boundary (compose, don't conflate):** TEE key-to-enclave binding — the attested identity a registry might consume — is **attestation's** domain (REPORTDATA/DCAP/measurement semantics), not this kit's; this kit may host the registry *shell* but defers what it verifies. A **bond gates correctness, not access** — separate concern (the delegation answers "may they read this?"; the bond answers "is the claim correct?"). Cross-org trust composes all three: binding (provenance) + delegation (authority — this kit) + bond (correctness).
