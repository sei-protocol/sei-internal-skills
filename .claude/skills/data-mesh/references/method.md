# The method — designing & reviewing data architecture

Two modes, one spine: **design** (architecting domains, data products, contracts, governance) and **review** (a lens over an existing or proposed data architecture). Both load the profile + kit first, run the **fit-check before anything else**, judge against the profile's cross-org conventions before the generic canon, and rank trust/governance findings above style.

## The four stages

1. **Load.** `data-mesh-profile.md` (always first — its cross-org conventions override generic single-org Data Mesh habit) + the kit(s) for the concern (domain decomposition, data products & contracts, federated governance, self-serve platform, data quality/observability, interoperability/lineage). If working in a target system, read its governing docs; the live system wins over this snapshot — flag drift.
2. **Run the fit-check (stage 0, gate everything on it).** Before recommending a mesh, ask: is the org large/complex enough that decentralization beats a central team? Is ownership real or governance theater? Will federated governance gridlock? Is there sprawl risk? **If a lakehouse + a good central team delivers the value, say so** — don't design a mesh the org doesn't need. (The cross-org use-case is the strongest *fit* case — decentralization is forced there, not chosen.) Only proceed to the dimensions once mesh is the right answer for the slice in scope.
3. **Read the whole target.** For review: the domain boundaries + owning teams, each data product's contract (schema/semantics/SLOs/ports), the governance split (global vs local) and *how* it's enforced, the self-serve platform's coverage, the quality/observability instrumentation, the lineage + interoperability conventions. For design: the existing domains/products in scope. Never review a data architecture from a generic single-org mental model — the cross-org setting diverges (no trusted operator, verifiable products, computational governance, provenance-as-circuit-breaker) in ways a default reading gets wrong.
4. **Apply the six dimensions** (below), profile-first. Each finding cites a `sources.md` anchor and/or a profile rule. Rank trust/governance/one-way-door findings above style. Hand the contract *implementation* to `/evm` (gating/bonding), the attestation *design* to `/tee`, the telemetry backend to the observability agents.

## The six dimensions (the scorecard)

Grounded in the external canon (`sources.md`) and specialized by the profile's cross-org use-case.

1. **Domain decomposition & ownership.** Boundaries drawn along business domains (DDD), with a clear team accountable end-to-end (autonomy + accountability), not a central team in disguise. Cross-org: the domain boundary is also the **trust boundary** — name which org/registry owns each namespace and who may grant access. *Basis:* `sources.md` §principles, §fit-and-failure-modes; profile §1.

2. **Data-product design & contracts.** Each product is the **architectural quantum** (code + data/metadata + infra) satisfying the six usability attributes (discoverable, addressable, trustworthy, self-describing, interoperable, secure); contracts expressed in a real standard — **ODCS v3.x**, *not* the deprecated Data Contract Specification — with schema + semantics + SLOs + versioned ports. Cross-org: the product is a **verifiable certificate** (content-address, signature, provenance, verification class, optional bond), not a trusted-pipeline output. *Basis:* `sources.md` §data-product, §data-contracts; profile §2.

3. **Federated computational governance & policy-as-code.** Clean global (interoperability, identity, security, the ontology) vs local (domain models) split; global policy **enforced automatically** (policy-as-code / gating / bonds), not manually attested; the guild empowered but not a bottleneck (gridlock risk). Cross-org: enforcement is **operator-independent** (read from a neutral venue); the thin neutral registry is the moat — keep it small/objective/fail-closed/time-locked/irreversible/transparent. *Basis:* `sources.md` §federated-governance; profile §4.

4. **Self-serve platform leverage.** Does the platform cover the three planes (infra provisioning · data-product developer experience · mesh supervision) and genuinely **reduce domain cognitive load**, or push undifferentiated heavy-lifting onto domains (sprawl)? Cross-org: access is bounded/scoped/push-capable with per-assertion provenance — never a whole-graph dump. *Basis:* `sources.md` §self-serve-platform; profile §8.

5. **Data quality, observability & SLOs.** The five pillars (freshness, volume, distribution, schema, lineage) monitored; SLOs published on products; the "trustworthy" attribute made operational/measurable. Cross-org: the **claim-class taxonomy** governs what a quality guarantee can be — bond only **re-checkable Class-I** (re-execution/proof) **or dispute-adjudicable Class-II** (with a sound, capture-resistant dispute layer) claims; represent Class-III judgment as signed opinion + consumer policy, never a correctness bond; **authenticity ≠ correctness ≠ truth**. *Basis:* `sources.md` §observability; profile §5, §3.

6. **Interoperability & lineage.** Global addressing/identity conventions; polyglot output ports; end-to-end lineage (**OpenLineage**); a coherent contracts + product-descriptor strategy (contract-level **consolidating on ODCS**; the product-level **ODPS/DPDS** layer is unsettled — pick deliberately there, don't assume a winner). Cross-org: the namespace **extends without migration** (dimensions ≠ identity); leaf grammars embed external standards verbatim. *Basis:* `sources.md` §interoperability, §observability; profile §7.

## Design discipline (when authoring, not just reviewing)

- **Fit before mesh.** Argue the maximum scope you'd defend, then name what you'd cut first for an MVP — but *first* confirm mesh is even the right answer; the honest recommendation is sometimes "a lakehouse + a central team, not a mesh."
- A change touching **a domain/namespace authority binding, a published data-product contract or port, the shared ontology, an EIP-712-style governance type hash, or a deployed gating/bonding configuration** is a **one-way door** — consumers and outstanding grants depend on it; flag for human approval, never assert.
- Reach for the profile's cross-org reality over the generic single-org one: trust the **verifiable product**, not the pipeline; enforce governance **computationally + operator-independently**, not by a trusted platform team; expose **provenance per assertion** so a consumer can verify-before-act.
