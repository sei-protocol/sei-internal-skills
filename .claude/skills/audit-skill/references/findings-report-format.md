# Findings Report — Format

The durable artifact produced by an audit. It is a **lineage artifact** (Design 13 — process-lineage relocation): it lands in the DRI's `<engineer>-designs` repo at `designs/<arc>/audits/<skill>-<YYYY-MM-DD>.md` (repo-default arc `sei-internal-skills-stack` for sei-internal-skills), with the in-repo `docs/skill-audits/<skill>-<YYYY-MM-DD>.md` as the no-DRI-repo fallback (only when no DRI repo is resolvable and the user confirms; see *Report path conventions*). Generated by `scripts/findings-report.sh` from the merged JSONL findings.

## Template

```markdown
---
skill: <skill-name>
shape: <inferred-shape>
audited_on: <YYYY-MM-DD>
auditor: <git user.name>
audit_skill_version: 1
phase: <audit-only | audit+refactor>
---

# Skill Audit — <skill-name>

**Shape:** <discipline | technique | pattern | reference | procedural>
**Audited:** <YYYY-MM-DD> by <auditor>
**Phase:** <audit-only | audit+refactor>

## Summary

- **Block:**  <N>
- **Warn:**   <N>
- **Info:**   <N>
- **Skipped:** <N>  (rules that couldn't be evaluated — see end of report)

<one-paragraph summary of the audit, lead with the load-bearing findings>

## Block findings

> Severity: **block**. The skill is not ready to ship with these outstanding.

### <ID> — <one-line title>

- **Rule:** <conventions-catalog rule statement>
- **Source:** <static | semantic | pressure>
- **Evidence:** <observation from the check>
- **Recommendation:** <how to fix>

(repeat per block finding)

## Warn findings

> Severity: **warn**. Address before broad rollout.

(same format)

## Info findings

> Severity: **info**. Observations worth surfacing.

(same format)

## Pressure scenarios

> What the skill was tested against and how it responded.

### Scenario <id> — <one-line scenario title>

**Pressure mix:** <time + sunk-cost + authority + ...>
**Correct option:** <A | B | C>
**Subagent's choice:** <A | B | C>
**Result:** <pass | partial-fail | fail>

**Subagent reasoning (verbatim):**

> <full verbatim quote of the subagent's rationale>

**Finding ID:** <P7.scenario-id>

(repeat per scenario)

## Skipped checks

> Rules that couldn't be evaluated in this audit pass. The auditor should look at these manually.

- **<ID>** — <reason for skip>

## Refactor (Phase 2 only)

> Only present if the audit ran Phase 2.

### Applied changes

- **<finding-ID>** — <one-line description of the change>; diff at `state/run-<ts>/proposals/<finding-id>.diff`

### Skipped changes

- **<finding-ID>** — <why skipped: user declined / can't auto-fix / structural>

### GREEN verification

After applying the changes, the same pressure scenarios were re-run:

- **Scenario <id>:** <previously failed | previously passed> → <now passes | still fails | new failure>

### REFACTOR cycles

- Cycle 1: <summary>
- Cycle 2: <summary>
- Cycle 3: <summary or "converged before cycle 3">

### New evals added

The following pressure scenarios were appended to `<skill>/evals/evals.json`:

- **<eval-id>** — <one-line description>

## References

- Conventions catalog: `.claude/skills/audit-skill/references/conventions-catalog.md`
- Audit methodology: `.claude/skills/audit-skill/SKILL.md`
- Related audits of this skill: <links to prior reports>
```

## Report path conventions

- **Default (lineage home):** `designs/<arc>/audits/<skill>-<YYYY-MM-DD>.md` in the DRI's `<engineer>-designs` repo (repo-default arc `sei-internal-skills-stack` for sei-internal-skills; Design 13). Resolve the DRI repo as `/design` does (`--designs-repo` → sibling `<engineer>-designs` checkout → ask; in a non-interactive run, HALT — never guess) and create the `audits/` directory under the arc if missing.
- **No-DRI-repo fallback (in-repo):** only when no DRI repo is resolvable **and the user confirms**, write in-repo. The default in-repo path is `docs/skill-audits/<skill>-<YYYY-MM-DD>.md`; if the target repo has a different skill-audits convention (e.g., a different docs root), honor it — audit-skill checks for `docs/skill-audits/`, `audits/skills/`, or a repo-root-level pattern, defaulting to `docs/skill-audits/` and creating the directory if missing.
- **Multiple audits same day:** suffix with run number — `<skill>-<YYYY-MM-DD>-2.md`.

## Rendering rules

The script (`findings-report.sh`) does the following:

1. Reads JSONL findings (static + semantic + pressure).
2. Groups by severity, then by source (static / semantic / pressure within each severity bucket).
3. Sorts by catalog ID within each group.
4. Skipped checks go to a dedicated section at the end.
5. Pressure scenarios get their own top-level section (they're load-bearing and have richer evidence than a single line).
6. Phase 2 sections only render when refactor was applied (input includes `refactor-applied.jsonl`).

## What good reports look like

- **Specific.** Every finding cites concrete evidence (line numbers, file paths, quoted text). Never "the description is bad" — always "description is 1180 chars (limit 1024)" or "description includes 'runs intake → research → drafts' which summarizes workflow (Obra CSO trap)".
- **Actionable.** Every finding has a recommendation. If the recommendation is "discuss with the team", say so explicitly — but most findings have a clear fix.
- **Traced.** Every finding links to its conventions catalog ID. The catalog is the source of truth; the report is a snapshot.
- **Reproducible.** Re-running the audit with the same skill state should produce the same report (modulo subagent variance, which is bounded for the deterministic checks).

## What bad reports look like

- **Vague.** "Several issues with the description." Concrete or it doesn't count.
- **Untraced.** Findings without a catalog ID — you can't tell what rule fired.
- **Untyped.** No severity. Everything looks equally important.
- **Verbose.** Wall-of-text summaries that drown the findings. The report should be scannable; the evidence is what's detailed.
- **Hidden skips.** A check that couldn't run should be visibly skipped, not silently dropped.

## Multiple audits over time

The same skill audited at different dates produces multiple reports. The conventions catalog may evolve between audits — that's expected. The reports are dated artifacts; a finding that was `info` last quarter and is `block` this quarter is a legitimate change.

When a skill is audited repeatedly, the latest report is canonical. Older reports are historical record — useful for diffing what changed and what was fixed.
