# PR conventions for onboarding

Used by `seictl onboard` when generating engineer onboarding PRs against `sei-protocol/platform`.

Last verified: 2026-04-28 against shipped `seictl onboard` (#81). The PR body template is embedded in seictl as `cluster/onboard_pr_body.tmpl` — when this file disagrees, the embedded template wins.

## Branch naming

| Purpose | Pattern | Example |
|---|---|---|
| Onboarding (auto-generated by `seictl onboard --apply`) | `seictl/onboard-<alias>` | `seictl/onboard-bdchatham` |
| Engineer's later workload PRs (rare, hand-authored) | `<alias>/<short-description>` | `bdchatham/seinode-pacific-1-archive` |

The `seictl/`-prefix on auto-generated branches keeps tooling-authored work distinguishable from hand-authored engineer work in the platform repo's branch list.

Most workloads are direct-applied via `seictl bench up`, not via PRs. PRs land only for resources that should live in GitOps (long-lived RBAC additions, namespace edits, quota tweaks).

## PR title

`onboard: engineer cell eng-<alias>`

## Commit message

`feat(engineers): onboard <alias> cell` (conventional commits, scope = `engineers`)

## PR body template

The embedded template is intentionally minimal — Flux-tracked changes need only the load-bearing facts:

```markdown
Onboards engineer <alias>.

Namespace: eng-<alias>
Generated files:
- clusters/harbor/engineers/<alias>/namespace.yaml
- clusters/harbor/engineers/<alias>/bench-seiload-sa.yaml
- clusters/harbor/engineers/<alias>/kustomization.yaml

AWS resources (already provisioned out of band):
- IAM policy: <policy-arn>
- IAM role: <role-arn>
- Pod Identity: bench-seiload SA in eng-<alias>

Generated by `seictl onboard --apply`.

Reviewer checks:
- Alias <alias> is not already squatted in clusters/harbor/engineers/.
- ServiceAccount has no eks.amazonaws.com/role-arn annotation (Pod Identity binds server-side, not via annotation).
```

The rendered body is plain text — no Markdown headings — because it surfaces in `gh pr view` as the body and as a commit message extension if reviewers squash-merge.

## Reviewer conventions

- Reviewers: platform team (auto-assigned via CODEOWNERS once configured)
- SLA: same-day for onboarding PRs (engineer is blocked until merge)
- What reviewers check (mirrors the body's "Reviewer checks" section):
  - Alias matches an active platform engineer
  - `clusters/harbor/engineers/<alias>/` doesn't already exist (no squat)
  - Cell labels look right: `app.kubernetes.io/managed-by=flux`, `tide.sei.io/cell-type=personal`, `tide.sei.io/owner=<alias>`
  - `bench-seiload` ServiceAccount has **no** `eks.amazonaws.com/role-arn` annotation (Pod Identity binds server-side via `(cluster, namespace, serviceAccount)`; the IRSA-style annotation is at best a no-op and at worst misleading)
  - No additional resources beyond what `seictl onboard` generates (no manual additions slipped in — engineers operate as cluster-admin via SSO today, so if a Role/RoleBinding shows up, that's deliberate scope work tracked at sei-protocol/seictl#80, not an onboarding PR)
